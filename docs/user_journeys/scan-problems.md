# Journey Scan Problems

This ledger preserves release-blocking defects found during the journey audit and the evidence that closed them. A resolved row is historical evidence, not an active blocker.

| ID | Severity | Status | Finding | Resolution evidence |
|---|---|---|---|---|
| SP-001 | release-blocking | resolved | Chat and image-generation 401 handling navigated to `/auth/login`, while the application login page is `/login`. | Both 401 paths now redirect to `/login` in `apps/ui/src/components/widgets/ChatPage.tsx`; UJ-004 exercises the browser chat authentication contract. |
| SP-002 | release-blocking | resolved | Cloudflare Access and app passkey/GitHub login were exposed simultaneously, creating a mixed-auth login-loop risk. | `AUTH_MODE` now selects one browser-auth authority. `/auth/methods` advertises passkey/GitHub only in `standalone` mode and Cloudflare Access only in `cf_access`; passkey/GitHub login endpoints reject `cf_access`. `apps/worker/test/auth_routes.test.ts` covers both modes and forbidden mixed-auth paths. |
| SP-003 | release-blocking | resolved | Test/config/journey sources could be ignored while scripts used `--passWithNoTests`, allowing a false-green release. | Test, Playwright/Vitest config, journey manifest, and screenshot source files are tracked and no longer globally ignored. The release gate runs the tracked unit/integration and Playwright journey/matrix suites. |
| SP-004 | release-blocking | resolved | Several authenticated-page API requests could receive 401 together and each start its own `/login` navigation, intermittently aborting a competing redirect. | `redirectToLoginOnce()` is now the shared browser-auth failure boundary for API, transcription, chat, and image requests. `apps/ui/test/api-auth-redirect.test.ts` proves simultaneous 401 responses cause exactly one navigation; the previously flaky anonymous Analytics denial passed 10/10 repeated browser runs. |
| SP-005 | informational | resolved-harness | Local `workerd` sometimes logged `Broken pipe` / `Connection reset by peer` while Playwright stopped its managed E2E server. | A manually persisted Wrangler server ran the same anonymous Analytics denial 10/10, remained healthy afterward, and logged no socket errors. The diagnostic is confined to managed-server teardown and is not a product request failure. |
| SP-006 | release-blocking | resolved | `vf doctor` authenticated `/v1/models` with the configured bearer key but queried session-only `/admin/quota`, so a valid CLI API key could never produce a fully healthy doctor result. | Added bearer-key-protected `GET /v1/quota`; CLI `usage()` now calls that route. Worker tests cover valid/revoked keys, the CLI journey covers configured doctor output, and UJ-003 covers quota access before and after key revocation. |

| SP-007 | release-blocking | resolved | Clean release installs put Wrangler under `apps/worker/node_modules/.bin`, while lifecycle commands only searched the workspace-root `.bin` and could fail with `wrangler` not found. | `resolveWranglerBin()` now prefers an explicit override, root-local Wrangler, then the Worker package Wrangler before PATH fallback. `apps/cli/test/lifecycle-cli.test.ts` covers all four resolution paths. |
| SP-008 | release-blocking | resolved | A fresh workers.dev deployment could briefly return a transient non-ready response, causing `vf setup` to mark a healthy installation failed during Cloudflare propagation. | `WranglerProvider.health()` now retries bounded transient failures for up to roughly 30 seconds. Unit coverage proves recovery after 404/network failures, and the subsequent live clean setup completed on its first run. |
| SP-009 | release-blocking | resolved | Setup/update persisted migration names only after deployment health succeeded, so a later failure could lose evidence of schema changes that had already been applied. | Lifecycle setup/update now checkpoint migration names immediately after Wrangler reports successful application. Failure-path tests prove later health failures retain migration evidence; live setup receipts recorded all migrations before further acceptance steps. |
| SP-010 | release-blocking | resolved | Deleting a user created through an invite returned 500 because `auth_invites.used_by` retained a foreign-key reference to that user. | `deleteUser()` clears only `used_by` in the same D1 batch before deleting the user; `used_at` remains intact so the invite stays consumed. The invite regression proves deletion succeeds and replay still returns `consumed`; the same path was re-proven against live Cloudflare. |

| SP-011 | release-blocking | resolved | A clean installation had an empty model catalog until the owner manually ran model sync, so first-run chat could show no usable model. | `ensureModelCatalog()` now performs one lazy Cloudflare catalog sync only when the models table has never been initialized; both `/admin/models` and `/v1/models` fail clearly on discovery errors instead of returning a misleading empty list. `model_catalog.test.ts` covers first sync, no repeated sync for disabled catalogs, and empty-discovery failure; UJ-001 requires a non-empty first-owner catalog. |
| SP-012 | release-blocking | resolved | Workers AI model families use different request/response shapes: reasoning text can live outside `message.content`, vision expects byte arrays, turbo/Deepgram STT expects base64, and Deepgram/raw-stream TTS shapes differ. | `translator.ts` now normalizes those shapes while preserving newer image/error handling. `translator_modalities.test.ts` covers reasoning responses/streams, vision bytes, classic-vs-turbo STT, Deepgram TTS input, base64 output, and raw streamed audio. |
| SP-013 | release-blocking | resolved | Browser chat selected the first alphabetic text model after sync, making first-run success depend on Cloudflare catalog ordering. | `ModelPicker` now prefers `@cf/meta/llama-3.2-3b-instruct`, which passed live Cloudflare acceptance, then known fallbacks, while retaining the full catalog. Unit coverage proves preferred selection and catalog-order fallback; UJ-004 remains green through the real Astryx selector. |

| SP-014 | release-blocking | resolved | Exact-tag clean-account acceptance exposed a first-run catalog race: the lazy sync writes model rows page-by-page, so a concurrent Chat request could see the first rows, treat `COUNT(models) > 0` as initialization complete, and lock the selector onto an early alphabetic model before the full catalog arrived. | Catalog readiness now uses a durable `system.model_catalog_ready` marker written only after complete sync/reconciliation, plus same-isolate single-flight. Manual and cron refreshes use the same completion path. `model_catalog.test.ts` covers partial-row visibility, concurrent first access, disabled initialized catalogs, and failed empty discovery; the full Worker suite is 77/77. |
